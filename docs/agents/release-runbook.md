# 归序 Orderly AI 发布运行手册

## 1. 文件定位

本文件面向执行发布任务的 AI 主代理和按需 subagent，不是用户操作教程。

当任务涉及完整版、运行包、离线源码包、安装器、发布校验、发布返工或 GitHub Release 时，AI 必须先读取本文件，再执行构建或回答“能否发布”。

本文件补充 `AGENTS.md`、`docs/agents/architecture-baseline.md` 和 `docs/agents/collaboration-workflow.md`，不扩大当前阶段允许的业务范围。

## 2. 强制目标

AI 发布工作的目标不是“尽快得到一个 EXE”，而是同时满足：

1. 正式资产来自干净提交。
2. 每个产物都能由清单和哈希追溯。
3. 完整版与离线源码包来自同一版本和同一源码树。
4. 测试、安装、启动、退出和卸载均有真实执行证据。
5. 一次冻结后只执行一轮正式打包，不通过反复全量打包来发现已知问题。
6. 未验证项必须明确保留，不得用“应该可以”替代执行结果。

## 3. 不可违反的规则

- 正式发布禁止使用 `-AllowDirtySnapshot`。
- 正式产物必须从干净工作树和已提交的精确 commit 生成。
- 冻结后不得继续修改源码、脚本、契约、版本号或发布文档。
- 冻结后任何代码或文档变更都立即使本轮正式产物失效，必须重新冻结和重新打包。
- 不得删除、跳过、弱化或吞掉测试来获得绿色结果。
- 不得手工修改生成目录中的清单、哈希、JAR、EXE、ZIP 或 jpackage 私有文件来“修复”校验。
- 不得把 jpackage 私有运行时元数据、缓存、日志、凭据、`.workbuddy`、`target`、`.git` 或本地 Maven 缓存发布出去。
- 不得在用户未明确要求时创建 Git Tag、GitHub Release、强制推送或改写远端历史。
- 推送失败时必须保留本地提交和正式资产，并如实报告；不得声称已上传。
- API Key 不得进入命令行、日志、响应、仓库、浏览器存储或普通配置文件。
- 删除仍只能进入项目回收站；不得用清理构建目录为理由删除用户数据。

## 4. 发布任务读取路由

AI 收到发布任务后按以下顺序读取：

1. `AGENTS.md`
2. `docs/repo-map.md`
3. `docs/agents/release-runbook.md`
4. `docs/agents/testing/README.md`
5. 当前版本涉及的打包、校验、配对和发布脚本
6. 相关契约、合法/非法样例和当前月测试记录

不得先运行全量打包，再通过失败结果反推发布边界。

## 5. 发布状态机

AI 必须显式区分以下状态：

| 状态 | 含义 | 允许动作 |
|---|---|---|
| `UNPREPARED` | 版本、脚本或验证边界尚未收口 | 只做检查和修复，不生成正式资产 |
| `DRY_RUN` | 使用临时输出验证发布链路 | 可重跑，不得标记正式发布 |
| `FROZEN` | 精确 commit 与发布参数已冻结 | 只执行一轮正式打包 |
| `VERIFIED` | 所有适用校验、安装与记录已完成 | 可提交发布结果 |
| `PUSHED` | 提交已真实到达目标远端分支 | 可交付 |
| `BLOCKED` | 外部网络、工具或权限阻止完成 | 保留证据并报告 |

每次报告当前状态时必须给出依据，例如 commit、命令、退出码、哈希或远端 SHA。

## 6. 正式打包前预检

在进入 `DRY_RUN` 前，AI 必须逐项确认：

- 当前分支、HEAD、目标远端和项目版本一致。
- 工作区无未提交源码变更；如果存在无关用户改动，先停止并报告。
- `pom.xml`、Python 包版本、完整版清单、安装器 `--app-version` 和离线包版本一致。
- WebView2 官方 SDK、WebView2 Runtime 模式与版本、C# 宿主源码和许可证文件完整。
- 发布脚本使用的 JDK、Maven、Wix、Python 和 PyInstaller 路径真实存在。
- 发布排除项覆盖 `.git`、`.workbuddy`、`target`、`.m2-repository`、日志、PID、缓存、虚拟环境、凭据和 jpackage 私有元数据。
- 源码文件排序规则在 Windows 大小写不敏感文件系统上稳定；中文路径不会因排序导致完整版和源码包指纹不一致。
- 清单和哈希的生成顺序正确：先完成会改变产物的步骤，再生成最终文件清单和校验和。
- 安装器生成后会重新写入最终校验清单，而不是沿用安装前快照。
- 完整版验证会排除 jpackage 生成的私有元数据，同时仍校验所有正式发布文件。
- 完整版和离线源码包的 manifest 都包含项目版本、源码 commit、源码树摘要和 JDK 主版本。
- 测试记录文件已准备记录命令、退出码、产物哈希和未验证项。

缺少任一项时，状态保持 `UNPREPARED`，不得进入正式打包。

## 7. Dry Run 要求

Dry Run 使用临时发布目录，不覆盖最终发布资产。

AI 至少验证：

1. 离线源码包结构和文件清单。
2. 严格 Maven 离线构建。
3. 完整版应用目录和文件哈希。
4. 完整版与离线源码包配对。
5. jpackage 私有元数据边界。
6. 安装器生成后最终清单仍有效。

Dry Run 发现发布脚本问题时，应立即回到 `UNPREPARED`，修复根因并重新开始预检。

不得把 Dry Run 产物改名为正式资产，也不得用 Dry Run 结果代替最终干净提交的验证。

## 8. 冻结与正式打包

进入 `FROZEN` 时必须记录：

- 精确 commit
- 项目版本
- 操作系统和 PowerShell 版本
- JDK、Maven、Python、PyInstaller 和 Wix 版本或路径
- 发布输出目录
- 使用的发布参数

冻结后按顺序执行：

```powershell
.\scripts\package-offline.ps1
.\scripts\verify-offline.ps1 <OFFLINE_ZIP> -MaxParallel 2
.\scripts\package-full.ps1 -OutputDirectory <ARTIFACT_ROOT> -MavenRepository .\.m2-repository -WixHome <WIX_HOME>
.\scripts\verify-full.ps1 -AppDirectory <FULL_APP_DIR>
.\scripts\verify-full-release-pair.ps1 -AppDirectory <FULL_APP_DIR> -SourcePackage <OFFLINE_ZIP>
```

只有在上述命令全部通过后，才能进入安装验收。

正式打包期间不得修改源码、脚本或契约。若必须修改，本轮产物全部作废，并从预检重新开始。

## 9. 安装器验收

安装器必须执行真实安装和卸载，不能只检查 EXE 存在。

AI 必须验证：

- 先卸载已有同名安装，避免旧文件污染。
- 正式 EXE 静默安装退出码为 0。
- 注册表显示的目标版本正确。
- 安装目录存在 `files.sha256`，且与正式构建目录一致。
- 安装目录通过 `verify-full.ps1`。
- 使用独立数据目录启动，不覆盖用户或开发数据。
- 业务模块、系统模块和主题数量的预期值来自当前 manifest，不得机械假设永远为 6/1/5。
- AI 代理在正式超时窗口内就绪；不得在宿主刚存活时立即断言 AI 服务失败。
- `/api/system/shutdown` 后启动器退出码为 0。
- 完整版启动后出现 WebView2 窗口，页面来自当前 `127.0.0.1` origin，没有打开默认浏览器。
- 关闭 WebView2 窗口后 `OrderlyWebView2Host.exe`、`msedgewebview2.exe`、Java、Python 和后台构建进程均退出。
- GitHub Actions 只验证能够自动化的结构、进程和接口；真实窗口显示、焦点、缩放和关闭交互必须在交互式 Windows 桌面完成人工验收并记录。
- 卸载后安装目录和卸载项被清除。
- 独立数据目录和保留标记文件仍存在。
- 卸载后没有引用安装目录的残留进程。

安装器未签名时必须如实说明 SmartScreen“未知发布者”风险，不得隐去。

## 10. 门禁和测试记录

正式发布提交必须执行与变更风险相符的完整门禁。

AI 必须在 `docs/agents/testing/records/YYYY-MM.md` 记录：

- commit
- 实际命令
- 退出码或通过/失败结论
- 离线 ZIP、完整版 ZIP、安装器和关键清单的 SHA-256
- 安装、启动、模块/主题、AI、退出和卸载结果
- 未验证项
- 失败后重试的真实原因

纯测试记录文档变更仍需执行 `.\scripts\doc-gate.ps1`。

## 11. 时间与停止条件

发布链路的正常目标：

- 预检和 Dry Run：10–20 分钟
- 正式离线包与完整版：15–25 分钟
- 安装、卸载和门禁：10–15 分钟
- 首次干净发布总目标：不超过 60 分钟

出现以下任一情况时必须停止继续全量打包并重新定位根因：

- 同一类发布错误连续出现两次。
- 最终清单、哈希、配对或安装器校验反复失效。
- 冻结后出现新源码变更。
- 无法解释残留进程、文件或版本差异。
- 最终打包超过 30 分钟仍无有效进度。
- 推送或外部工具网络失败，但本地证据尚未整理。

停止不是交付失败。正确做法是报告当前状态、根因假设、实际证据和下一步最小验证。

## 12. `0.1.0` 返工记录

`0.1.0` 从首次发布准备到最终记录约 3 小时 08 分。最终成功干净打包约 24 分钟，其余时间主要消耗在五轮发布边界返工：

| 问题 | 根因 | 后续预防 |
|---|---|---|
| `.workbuddy` 被发布 | 发布文件收集只依赖 Git 跟踪状态，没有统一排除内部协作目录 | 发布预检固定检查排除项，并增加产物清单断言 |
| 中文路径导致指纹不一致 | 完整版和离线包使用了不同的路径排序规则 | 统一大小写不敏感、稳定的相对路径排序 |
| 安装器校验和失效 | 校验和在安装器完成前生成，后续步骤再次改变文件 | 所有改变产物的步骤完成后再生成最终清单 |
| jpackage 私有元数据被校验 | 发布校验把 jpackage 运行时内部文件当作正式资产 | 建立明确的 jpackage 私有路径排除清单 |
| 排除范围不完整 | 首次修复只覆盖部分私有元数据 | 对 `app/.jpackage.xml`、`app/.package` 等已知边界做完整验证 |

这些问题的修复已进入发布脚本和测试记录。AI 不得重新用全量打包验证已经修复的旧问题；应先用定向脚本检查或 Dry Run 证明回归边界。

## 13. 验证结果判定

AI 只有在以下条件全部满足时才能宣布正式发布完成：

- 状态已达到 `PUSHED`。
- 正式资产来自冻结 commit。
- 离线构建、完整版校验和双包配对全部通过。
- 正式安装器完成安装、运行和卸载验收。
- 完整门禁通过。
- 测试记录包含真实命令和产物哈希。
- 未验证项已明确列出。
- 本地与远端分支一致，或推送失败已如实报告。

缺少任何一项时，使用 `CONDITIONAL` 或 `BLOCKED`，不得使用“已完成”。

## 14. 后续优化约束

`0.1.1` 及后续版本优先通过工程手段缩短发布时间：

- 增加发布预检脚本，先在数秒级检查排除项、版本、清单顺序和冻结状态。
- 增加单入口发布脚本，避免人工漏掉配对和安装验收。
- 清理或限制历史 `target/build-parallel-*` 目录，只保留最近需要的日志。
- 评估使用 `jlink` 裁剪 JDK，并评估共享 jpackage runtime 与构建 JDK。
- 缓存可复用的 AI 和 Maven 构建产物，但不得发布缓存或跳过必要验证。
- 将已知发布回归做成自动化测试，而不是继续依赖会话记忆。

AI 不得把“压缩包很大”或“jpackage 没输出”作为跳过验证的理由。
