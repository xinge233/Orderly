# Subagent 协作与质量门禁

本文件定义主代理、项目经理、软件工程师和界面设计角色卡包之间的完整协作流程。所有状态与结论必须基于实际文件和可复现证据。

## 1. 权责分离

| 角色 | 可以做什么 | 不可以做什么 |
|---|---|---|
| 主代理 | 拆解任务、调度 subagent、处理冲突、最终检查与交付 | 只凭 subagent 报告宣布完成 |
| `project_manager` | 定义范围、审查模块化与测试报错、给出验收结论 | 修改文件、实施修复、批准自己的产出 |
| `software_engineer` | 在批准范围内修改文件、运行检查、提交交接报告 | 扩大范围、修改验收标准、自行最终通过 |
| `ui_design_lead` | 默认只读审查外观、布局、动画、可访问性和视觉状态；获 PM 批准后修改授权 UI 文件 | 修改后端、契约、模块业务代码、自行批准或扩大接口 |

最终裁决权属于主代理，业务范围和阶段边界的解释权属于用户。

## 2. 标准流程

### 2.1 主代理下单

主代理必须先明确：

- 当前任务目标
- 当前处于首版实现阶段
- 允许读取和修改的路径
- 明确非目标
- 期望交付物
- 是否存在并行任务

简单事实查询可以单代理完成。跨文件、需要审查或可能越界的任务必须使用 subagent。

### 2.2 PM 开工预检

PM 阅读根规则、架构基线和任务资料后，使用 `templates/task-brief.md` 输出任务卡。

预检必须回答：

- 任务是否属于当前阶段
- 是否存在应禁止的代码、AI、业务模块或 UI 实现
- 文件职责是否清晰
- 模块边界和依赖方向是否明确
- 验收标准是否可验证
- 当前必须执行哪些构建、测试和烟测
- 是否阻塞等待主代理或用户决策

任务卡结论为 `READY` 时，主代理才可安排软件工程师开工。结论为 `BLOCKED` 时，不得进入实施。

### 2.3 软件工程师实施

软件工程师只修改任务卡列出的文件，并遵守：

- 修改前先读取现有文件和相关引用
- 保持最小差异
- 不新增未批准依赖、顶层目录或伪实现骨架
- 不覆盖无关修改
- 不伪造验证结果
- 遇到范围歧义立即停止并报告

首版实现阶段必须执行真实构建、测试和烟测；文档一致性检查不能替代应用验证。

界面设计类任务可先由 `ui_design_lead` 角色卡包做只读审查和方案设计。若进入实现，PM 必须单独列出允许修改的 UI 文件；未列出的前端逻辑、宿主、契约、模块 Java 代码和脚本一律不得改动。视觉实现完成后，PM 仍需独立验收，不采用角色自评代替验收证据。

### 2.4 软件工程师交接

使用 `templates/software-engineer-handoff.md`，至少提供：

- 状态
- 修改文件
- 变更摘要
- 边界检查
- 实际检查命令与结果
- 风险和未决事项

状态定义：

| 状态 | 含义 |
|---|---|
| `DONE` | 范围内工作已完成且有验证证据 |
| `DONE_WITH_CONCERNS` | 已完成，但存在需 PM 判断的风险 |
| `BLOCKED` | 无法继续，需要主代理或用户补充信息 |

### 2.5 PM 独立验收

PM 必须直接读取实际文件，不能只阅读交接报告。

使用 `templates/pm-review.md`，检查：

- 范围是否符合任务卡
- 是否有未授权文件或代码
- 文件职责是否单一
- 引用是否有效
- 规则是否重复或冲突
- 首版实现范围与 V7 未交付能力是否分离
- 测试状态是否真实
- 是否隐瞒报错或未验证项
- UI 占位表达是否诚实

结论定义：

| 结论 | 含义 |
|---|---|
| `PASS` | 范围、文件职责、事实和验证证据均满足 |
| `CONDITIONAL` | 主体可接受，但有非阻塞项需主代理记录或后续修复 |
| `FAIL` | 存在范围越界、关键缺失、事实错误、冲突或虚假验证 |

存在任何阻塞问题时不得给出 `PASS`。

### 2.6 主代理最终检查

主代理需要：

1. 核对实际文件清单与任务卡。
2. 检查 PM 和工程师结论是否一致。
3. 处理分歧，必要时发起一轮定向返工。
4. 确认没有代码、依赖、未来目录或虚构测试。
5. 向用户报告交付文件、验证情况和未决风险。

## 3. 返工流程

PM 给出 `FAIL` 或阻塞项时：

1. 主代理把返工项转换为新的最小任务，不重新开放整个任务范围。
2. 软件工程师只修复指定项。
3. 软件工程师重新提交交接报告。
4. PM 只针对返工项和相关影响面复核。
5. 同一阻塞连续两轮未解决时，停止并请求用户决策。

禁止通过删除规则、弱化验收标准、跳过检查或隐藏报错来消除返工。

## 4. 并行规则

- 优先并行执行只读分析、资料核对、测试日志归纳等互不干扰的任务。
- 写任务只有在文件集合完全不相交时才可并行。
- 两个 agent 不得同时修改同一文件。
- PM 验收与软件工程师修改不得并行作用于同一产出。
- 主代理负责在并行结果返回后检查冲突和一致性。

## 5. 首版实现的专项门禁

PM 与软件工程师至少检查：

- 框架不包含具体业务能力
- 框架不直接依赖具体模块实现
- 模块自包含且可安全移除
- 契约是唯一真相源
- 契约合法/非法样例存在
- 跨语言契约变更同步
- 授权、快照与回滚不可被模块绕过
- 删除只进入回收站
- 状态机非法迁移与依赖环有测试
- 路径边界与回滚幂等性有测试
- 前端类型检查、构建和样式变量检查通过
- 最低 UI 结构完整，且未实现能力明确标注为占位
- 外观与动画变更尊重主题取值、模块自有 UI、动效关闭和 `prefers-reduced-motion`
- 空模块、加载失败、错误、禁用状态和窄屏布局均有实际检查证据
- 所有测试失败和环境问题均原样报告

具体命令由任务卡和 README 明确，默认门禁为：

```powershell
.\scripts\gate.ps1
.\scripts\start.ps1
.\scripts\smoke.ps1
```

门禁必须保留真实退出码和报错。没有实际命令结果时，不得声称通过。

## 6. 交接摘要格式

subagent 返回主代理时，正文保持简短，详细证据可写入模板指定内容：

```text
状态：
任务编号：
范围结论：
修改文件：
验证：
阻塞/风险：
需要主代理决定：
```

PM 的最终摘要必须包含 `PASS`、`CONDITIONAL` 或 `FAIL` 以及文件级证据。
