# 06 · 派发话术

> 读者：编排者（人）。这份文件回答一个操作问题：**每次到底往 agent 里输入什么。**
> 核心原则一句话：**给指针，不给内容。**

---

## 1. 为什么不能全塞

14 个文件约 2200 行、接近 3 万 token。全塞进去有三个具体后果：

1. **贵。** 每轮对话都要带这 3 万 token，多轮下来是纯浪费。
2. **会迷路。** `02` 和 `03` 都描述插槽，`04` 和 `05` 都提门禁，`AGENTS.md` 又复述了一遍十条。全读会让 agent 分不清哪份是权威。
3. **会僵化。** 它会把不该当前置条件的东西当前置条件（例如明明只需要写界面，却去纠结契约字段）。

**正确做法：你只给"哪个文件 + 干什么"，文件内容由它自己 `read`。** agent 有文件读取工具，让它读比你贴更快也更准。

## 2. 三种场景的开场白

### 2.1 场景 A：单会话，让 Codex 自己分工（最省事）

在仓库根启动 `codex`，第一句：

```
按 AGENTS.md §4.2 的委派规则推进 tasks/S1-skeleton.md。

顺序要求：
1. 先派 guardian，只做 §3，结束时要它明确给出"契约已冻结"或"未冻结+缺哪条"
2. 冻结后并行派 engineer（§5）与 ui（§4）
3. 最后派 pm 按 §9 验收，结论只能是"通过"或"打回"

每阶段结束把交接记录写到 tasks/S1-<角色>.handoff.md，六段格式见 tasks/_TEMPLATE.md。
不要一次读完 prompts/ 下所有文件，按各角色 md 里的"开工前按顺序读这些"自行读取。
```

最后一句是关键。不写它，agent 常常会为了"稳妥"把整个 `prompts/` 扫一遍。

### 2.2 场景 B：四个终端，手工派角色（最可控、最省 token）

每个终端一个角色，靠 `tasks/*.handoff.md` 串起来。四个终端依次开：

```
# 终端 1（第一个开）
cd <repo-root> && codex
> 完整读取 prompts/roles/contract-guardian.md，然后按 tasks/S1-skeleton.md §3 开工。
> 只读它"必读顺序"里点名的文件，不要预读其它。
```

```
# 终端 2（等终端 1 说出"契约已冻结"后再开）
cd <repo-root> && codex
> 完整读取 prompts/roles/engineer.md，然后按 tasks/S1-skeleton.md §5 §7 开工。
> 先读 tasks/S1-guardian.handoff.md 确认契约已冻结。
```

```
# 终端 3（与终端 2 同时开）
cd <repo-root> && codex --sandbox workspace-write
> 完整读取 prompts/roles/ui-engineer.md，然后按 tasks/S1-skeleton.md §4 §8 开工。
> 先读 docs/UI-SPEC.md 拿到插槽名。不要改 web/ 以外的任何文件。
```

```
# 终端 4（等 2、3 都交了交接记录再开）
cd <repo-root> && codex
> 完整读取 prompts/roles/pm.md，然后按 tasks/S1-skeleton.md §9 验收。
> 只读三个角色的交接记录和门禁报错指向的位置，不要通读实现代码。
```

### 2.3 场景 C：没有文件读取能力的环境（网页聊天框）

只有这一种情况需要贴正文。贴的量：

| 贴什么 | 不贴什么 |
|---|---|
| `AGENTS.md` 全文 | `prompts/02`~`05`（让它需要时自己说"请给我 02 的内容"） |
| `prompts/00` + `prompts/01` | 其它三个角色的 md |
| 你当前角色的那一份 `prompts/roles/*.md` | `tasks/` 全部 |

合计约 640 行，是这个包里"任何角色都必须知道"的最小集。其余按需追加。

## 3. 续接话术

多轮对话时**不要重述上下文**，只指路：

| 情况 | 说什么 |
|---|---|
| 接着上一轮干 | `继续。先读 tasks/S1-<角色>.handoff.md 恢复上下文，再继续 §5 剩余项。` |
| 上一轮被 pm 打回 | `读 tasks/S1-pm-review.md 的"打回清单"，只修那几条，不要顺手改别的。` |
| 想让它换个角色 | `现在换成 pm 角色：完整读取 prompts/roles/pm.md，按它执行，不要沿用上一个角色的判断。` |
| 它开始跑偏 | `停。回到 AGENTS.md §1 的十条，逐条对照你刚才的改动，指出违反了哪条。` |
| 它想加字段/加目录/加依赖 | `这属于 §5 决定权表里"必须问"的项。先写在交接记录里，不要动手。` |

第 4 条很好用：让 agent 自己对照红线自检，比你说"你错了"有效得多。

## 4. 上下文预算

按这套方式，每个角色实际进上下文的量：

| 内容 | 行数 | 何时 |
|---|---|---|
| `AGENTS.md` | 260 | 自动 |
| `prompts/00` + `01` | 250 | 开工时 |
| 自己的角色 md | 140 | 开工时 |
| 任务卡的相关节 | 30~60 | 领任务时 |
| 按需的 1~2 份规范 | 150~350 | 遇到具体问题时 |
| **合计** | **约 850~1050 行** | 对比全塞的 2200 行 |

省下来的一半不是钱的问题，是**注意力**的问题。规范文件的价值在于"需要时能查到"，不在于"提前背下来"。

---

## 5. 三个反模式

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 把 14 个文件贴进第一条消息 | agent 会挑错权威文件，且后续每轮都在付这 3 万 token | 只给 `AGENTS.md`（自动）+ 角色 md 路径 |
| 每次续接都重述一遍要求 | 你的重述会和文件里的条款产生细微差异，agent 只能二选一 | 让它读交接记录恢复上下文 |
| 一句话给一个角色干完所有事 | `pm` 不独立就没有"否决"，`guardian` 不先跑契约就会被实现反向塑形 | 至少保证 `guardian` 先行、`pm` 独立 |

第三条最容易被忽略，也最贵。四个角色挤在一个会话里，等于把"互相制衡"变成"自己检查自己"。

---

## 6. 一页速查

```
第一句只给三样：入口文件 + 角色文件 + 任务卡的节号
不给：其它 prompts、其它角色 md、tasks 全文
续接只给：交接记录的路径
跑偏时说：对照 AGENTS.md §1 逐条自检
```

是否需要追加文件，让 agent 自己提："我需要 `02` 的字段表" ——它提出来你再给，比你先塞准。
