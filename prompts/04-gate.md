# 04 · 门禁

> 读者：`engineer`（实现门禁）、`pm`（跑门禁并解读报错）、全体（读懂为什么失败）。
> 落盘目标：`scripts/gate.cmd` + `scripts/gate.ps1`。

---

## 1. 门禁是什么

门禁是"完成"的唯一判据。它的存在不是为了拦住错误，而是为了把**"做完了"这件事从主观判断变成一条命令的输出。**

一条规则：**门禁失败时改代码，不要改门禁。** 门禁脚本的修改权只属于 `engineer`，且每次修改需要 `guardian` 复核并在交接记录里写明理由。

---

## 2. 调用方式

```
scripts\gate.cmd            完整模式，合并前必须跑
scripts\gate.cmd -Fast      跳过测试，仅用于本地迭代
```

不要直接运行 `.ps1`——本机执行策略默认为 Restricted，会被拒绝。`.cmd` 内部已带 Bypass。

---

## 3. 检查项

S1 共八项。任一项失败即整体失败，输出里要能一眼看出是哪一项。

| 编号 | 检查 | 通过条件 | 失败信息必须包含 |
|---|---|---|---|
| G1 | 目录白名单 | 顶层只有 `AGENTS.md prompts tasks contracts control web docs scripts`（点开头的目录不参与，但要列出白名单：`.git` `.codex` `.workbuddy`） | 违规目录名 + 建议动作 |
| G2 | 越阶段检查 | 无 `ai/`、无 `.py` 文件、无新增依赖 | 文件路径 |
| G3 | 契约一致性 | `module.schema.json` 自身合法；`registry.json` 通过该 Schema；非法样例被拒绝且报错指到字段 | 出错的字段名 |
| G4 | 编译与单测 | 控制层编译通过；`-Fast` 时跳过单测 | 首个错误的文件:行 |
| G5 | 分层依赖 | `api → kernel`，`kernel` 不反向依赖 `api`；模块不互相依赖 | 违规的包名对 |
| G6 | 空注册表启动 | 以 0 模块启动成功，健康检查返回结构化状态 | 实际模块数 |
| G7 | 样式门禁 | `web/` 除 `themes/` 外：无十六进制色值、无 `rgb(`、无写死毫秒、无字体名 | 文件:行 + 命中的原文 |
| G8 | 界面骨架断言 | 三主体节点、设置弹窗、主题切换入口、空状态节点在 `index.html` 中存在 | 缺失的节点标识 |

### 3.1 关于 G3 的细节

契约检查包含三件事，缺一不可：

1. Schema 自己能通过 JSON Schema 2020-12 的元校验
2. `registry.json`（空注册表）通过该 Schema
3. 一份**故意写错**的样例被拒绝，且拒绝原因精确到字段（例如缺 `risk` → 报 `fs_probe: missing risk`）

第 3 条最容易被跳过。没有它的契约检查是自欺欺人：一个永远返回"通过"的校验器也能过前两条。

### 3.2 关于 G6 的细节

"以 0 模块启动"必须是**真启动**，不是"能编译"。做法：用一个专用的启动参数或测试用例，加载空注册表，断言应用进入就绪状态且健康检查返回 `status=ok`、`modules=0`。

如果这条过不了，说明框架里某个地方假设了"至少有一个模块"，模块化就是假的。

### 3.3 关于 G7 的细节

扫描范围：`web/**/*.css`、`web/**/*.html`、`web/**/*.js`。排除：`web/themes/**`。

四类命中：

- `#` 后跟 3/6/8 位十六进制
- `rgb(` / `rgba(` / `hsl(`
- 数字后跟 `ms` 或 `s` 的时长字面量
- 常见字体名（判断方式：`font-family` 的值不是变量引用）

允许的形式只有一个：`var(--xxx)`。

### 3.4 关于 G8 的细节

不做视觉比对，只做结构断言。要求 `web/index.html` 中存在以下可识别的锚点（`id` 或 `data-*`，命名由 `ui` 定，但必须写进 `docs/UI-SPEC.md`）：

- 侧边栏容器、搜索框、条目列表、设置按钮
- 主界面容器
- AI 对话栏容器
- 设置弹窗容器、关闭按钮
- 主题切换入口
- 空状态节点

这是"防删"而不是"防丑"。丑由 `pm` 按 `01-stage-scope.md` §5 判。

## 4. 报错怎么读

门禁的报错格式统一为：

```
<检查编号> <文件:行> → <问题> | <建议>
```

例：

```
G7 web/css/components.css:12 → hex color in non-theme file (#2E6BE6) | move to themes/default.json, reference var(--accent-primary)
G3 contracts/registry.json → fs_probe: missing risk | risk must be one of read_only/write/delete
G1 <repo-root> → unexpected directory: assets | move into web/ or apply RFC
```

读报错的顺序：

1. 看编号，先确定这是"结构问题"还是"实现问题"
2. G1/G2/G3/G5 是结构问题，改动往往牵涉他人，先看交接记录里有没有对应说明
3. G4/G6/G7/G8 是实现问题，就地修
4. 报错里带建议的，先按建议改；建议明显不适用时，改完在交接记录里说明为什么不按建议

---

## 5. 门禁与评审的关系

门禁全绿 **不等于** 可以合并。门禁只证明"结构没坏、能编译、能启动"，不证明"界面好看、交互对、契约合理"。后三者由 `pm` 与 `guardian` 判。

反过来，门禁红了 **一定** 不能合并，没有例外，不接受"先合并再修"。这条是团队纪律，不是技术选择。

---

## 6. engineer 实现门禁的顺序建议

1. 先做 G1 / G2 —— 最简单，且能立刻挡住越阶段行为
2. 再做 G4 —— 编译与测试是其余检查的载体
3. 然后 G3 —— 契约检查依赖 guardian 先交 Schema
4. 接着 G6 —— 依赖控制层骨架能启动
5. 再做 G5 —— 依赖包结构稳定
6. 最后 G7 / G8 —— 依赖 `web/` 有内容

前五项跑通之前，不要开始写 `web/` 相关检查，否则会反复调整正则而浪费一轮。

---

## 7. 门禁脚本自身的质量要求

- **一次运行输出全部失败项**，不要遇到第一个错误就退出（否则修一个跑一次）
- **总耗时控制在 90 秒内**（`-Fast` 模式 30 秒内），超时会让人跳过门禁
- **不产生副作用**：不写文件、不改数据库、不留临时目录
- **可重复运行**：连跑两次结果一致
- **在干净克隆的仓库上能跑通**：不依赖本机已有的构建缓存
